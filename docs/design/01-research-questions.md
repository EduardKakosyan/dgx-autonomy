# Research Questions

1. What environment actually exists on `dgx-1`, and what access and resource constraints apply? Through read-only SSH inspection, record OS/kernel/architecture, NVIDIA driver and CUDA toolkit, unified-memory availability and measurement caveats, storage/filesystems, Docker/Compose/runtime configuration and permissions, Python/venv/uv, Git, Node/npm, active services, development-directory conventions, and existing llama.cpp installations or NVIDIA-specific optimizations. Which findings come from direct inspection versus documentation, and which checks are blocked by permissions or unavailable tooling? Do not expose credentials or alter existing services.

2. What relevant implementations exist in the current local repository and in development repositories discovered on `dgx-1`, and how are they separated? Locate any inference launchers, agent SDK integrations, process supervisors, configuration loaders, sandbox definitions, persistent state, git automation, evaluators, and run logs. The initial local search found a beach-status Next.js application rather than an autonomy harness: explain the existing test/tooling contracts in `playwright.config.ts`, `e2e/`, `scripts/sim.ts`, `scripts/sim.test.ts`, and `.github/workflows/ci.yml`, without treating that application as an existing DGX harness. For existing frontend examples, what component library, color tokens with exact values, typography, spacing, borders, shadows, and theming are defined in `components.json`, `app/globals.css`, `components/beach-shell.css`, and `components/ui/`?

3. What do authoritative model repositories and current llama.cpp sources establish about the exact identities, availability, licensing, download authentication, and inference compatibility of `Qwen3.8-Flash-Next`, `Qwen3.6-35B-A3B`, `Qwen3-Coder-Next`, and any specifically identified DeepSeek coding models? Verify actual GGUF repositories, revisions, quantization filenames, shard sets, sizes, chat templates, tool-call formats, and runtime support rather than inferring them from names. For the initial model's approximately Q3 artifacts, what published or already measured evidence exists for weight residency, KV/cache costs, practical context limits, and throughput on a single 128 GB DGX Spark? Clearly distinguish verified artifacts and measurements from estimates and unsupported claims.

4. How does llama.cpp currently build and serve these architectures on DGX Spark GB10 with the installed CUDA stack? Trace official NVIDIA guidance and the relevant llama.cpp build/runtime documentation for ARM64, compute capability, supported CMake flags, GPU offload, unified memory, context/cache options, chat templates, sampling, and OpenAI-compatible tool calling. What are the actual health/readiness, request timeout/cancellation, error, concurrency, token usage, timing, and shutdown contracts? How do loopback binding and Docker networking affect endpoint reachability and exposure, and what existing services or occupied ports constrain it?

5. How does the current OpenHands Software Agent SDK implement headless local-model operation and agent lifecycle control? Identify exact package versions, supported Python/ARM64 platforms, public APIs and examples for `LLM`, agents, tools, conversations, Docker workspaces, structured events, interruption, continuation, persistence, and context condensation. Trace where model requests and shell/file tools execute, how tool-call parsing failures surface, which state and secrets are persisted, what survives a process/container restart, and whether context/token thresholds are directly exposed. Distinguish the SDK's model-client interface from its OpenAI-compatible agent-server gateway; document concrete compatibility blockers, if any, before investigating alternative SDKs.

6. What sandbox and browser-testing behavior is supported by the installed Docker stack, OpenHands workspace implementation, and current Linux ARM64 Playwright packages? Explain filesystem mounts and ownership, container user/capability defaults, resource limits, outbound-network controls, service discovery, port publishing, child-process cleanup, and access to host services. What versions and installation contracts exist for Node.js 22, pnpm, Python/uv, Playwright CLI, Playwright Test, and Chromium, and how do terminal/browser interfaces expose screenshots, console errors, interaction results, and test outcomes? What isolation boundaries govern host credentials, Docker access, evaluator files, supervisor code, and execution of untrusted application code?

7. What lifecycle, recovery, and durable-memory contracts are provided by existing code and the relevant SDK/runtime dependencies? Trace available process health signals, model OOM/hang/error reporting, agent crash and invalid-tool events, conversation rollover, pause/resume, workspace recovery, git checkpoint behavior, and fresh-context access to repository files. What guarantees and failure cases apply to persisted timestamps/deadlines, atomic state writes, interrupted checkpoints, dirty repositories, duplicate supervisors, inference contention between contexts, and clean termination of subprocess trees? Where existing mechanisms are absent, record absence rather than proposing new implementations.

8. What evidence and interfaces currently exist for independent evaluation, progress measurement, and reproducible run reporting? In existing tests, SDK events, llama.cpp responses, Docker metadata, and git history, identify available build/test results, application readiness signals, file changes, tool/LLM call counts, token usage, TTFT, throughput, restarts, compactions, and version identities. Explain how external browser/API evaluators access an application without exposing their source, what trust assumptions apply to agent-authored tests and status files, and which signals distinguish verified improvement from activity alone. Which integration-test capabilities already exist for checkpoint inspection, forced-restart/resume verification, browser inspection, evaluator execution, and final reporting, and which metrics or provenance values are unavailable or only estimates?
